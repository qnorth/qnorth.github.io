Setup and teardown for Go subtests

2026-10-25

Go’s testing package has no setUp() and tearDown() hooks, and you don’t need a framework to get them back. An anonymous struct with 2 function fields, plus t.Cleanup(), gives each subtest a fresh fixture and a guaranteed cleanup. This article presents a pattern, explains why it uses t.Cleanup() instead of defer, and points out where to pay attention.

The equivalents of PHPUnit’s Data Providers in Go: Table-Driven Tests

The Go Wiki recommends table-driven tests. You list the test cases in a []struct {...} slice or a map[string]struct {...} map and run each one as a subtest with t.Run(), which Go has supported since 1.7. Dave Cheney’s article “Prefer table driven tests” goes into much detail about using this nice technique.

 1func TestReverse(t *testing.T) {
 2	tests := map[string]struct {
 3		actual   string
 4		expected string
 5	}{
 6		"empty string":      {actual: "", expected: ""},
 7		"one character":     {actual: "x", expected: "x"},
 8		"palindrome string": {actual: "level", expected: "level"},
 9		"plain word":        {actual: "abc", expected: "cba"},
10	}
11
12	for name, tc := range tests {
13		t.Run(name, func(t *testing.T) {
14			t.Parallel() // Marks each test case as capable of running in parallel with each other.
15			if got := reverse(tc.actual); got != tc.expected {
16				t.Fatalf("reverse(%q) = %q, expected %q", tc.actual, got, tc.expected)
17			}
18		})
19	}
20}

🟠 Warning

Storing the cases in a map has a side effect worth keeping. In Go the iteration order over maps is not specified and is not guaranteed to be the same from one iteration to the next. If one case quietly depends on another running first, the test fails sooner or later instead of hiding the dependency for years.

If you come from PHP like me, this is what PHPUnit Data Providers do, and the Go version covers the same ground with less machinery. One PHPUnit feature has no counterpart, though: fixtures with setUp() and tearDown().

Keep the setup logic out of the test body

A fixture can be a single object or a whole object graph. As it grows, the code that builds it grows too, and the assertions drown in setup noise. PHPUnit solves this with 2 template methods. It calls setUp() before each test method and tearDown() after it, whether the test passed or failed.

In practice the 2 methods are not symmetric. You need tearDown() only when setUp() touched something outside the test object: a static property, a database row, a file, a socket, or an environment variable. Database fixtures are the common case. You insert rows before the test and delete them after it, so the next test starts from a clean state.

Go’s standard library has no hook system that runs before and after each subtest, but you can still build one in a few lines.

An anonymous struct with setUp & tearDown fields

The test below checks a StockRepository against a real database. Each subtest needs the same two products in the stock table, and each must leave the table empty.

 1func TestStockRepository_Reserve(t *testing.T) {
 2	db := openTestDB(t)
 3	repo := NewStockRepository(db)
 4
 5	suite := struct {
 6		setUp    func(t *testing.T)
 7		tearDown func(t *testing.T)
 8	}{
 9		setUp: func(t *testing.T) {
10			t.Helper()
11
12			query := "INSERT INTO `stock` (`sku`, `quantity`) VALUES ('BOOK-1', 3), ('PEN-1', 0)"
13			if _, err := db.Exec(query); err != nil {
14				t.Fatalf("failed to seed stock: %v", err)
15			}
16		},
17		tearDown: func(t *testing.T) {
18			if _, err := db.Exec("TRUNCATE TABLE `stock`"); err != nil {
19				t.Errorf("failed to truncate stock: %v", err)
20			}
21		},
22	}
23
24	t.Run("reserves available items", func(t *testing.T) {
25		t.Cleanup(func() { suite.tearDown(t) })
26		suite.setUp(t)
27
28		if err := repo.Reserve(t.Context(), "BOOK-1", 2); err != nil {
29			t.Fatalf("Reserve() error = %v", err)
30		}
31
32		if got := repo.Quantity(t.Context(), "BOOK-1"); got != 1 {
33			t.Errorf("Quantity() = %d, expected 1", got)
34		}
35	})
36
37	t.Run("rejects an out-of-stock item", func(t *testing.T) {
38		t.Cleanup(func() { suite.tearDown(t) })
39		suite.setUp(t)
40
41		if err := repo.Reserve(t.Context(), "PEN-1", 1); !errors.Is(err, ErrOutOfStock) {
42			t.Fatalf("Reserve() error = %v, expected ErrOutOfStock", err)
43		}
44	})
45}

The openTestDB() function is an ordinary helper. It opens the connection and registers db.Close() on the parent test:

 1func openTestDB(t *testing.T) *sql.DB {
 2	t.Helper()
 3
 4	db, err := sql.Open("mysql", os.Getenv("TEST_DATABASE_DSN"))
 5	if err != nil {
 6		t.Fatalf("failed to open test database: %v", err)
 7	}
 8
 9	t.Cleanup(func() { db.Close() })
10
11	return db
12}

How the pattern works

Both closures capture db from the enclosing test function. The struct exists only inside TestStockRepository_Reserve, so the fixture sits next to the tests that use it and nothing leaks into the package scope - this keeps the things nicely encapsulated.

A package-level helper could do the same work, but it would need db passed in and would be visible to every other test in the package. I prefer the struct: the setup and the teardown read as one unit, the way they do in a PHPUnit test class.

Each subtest starts with the same two lines:

  1. t.Cleanup(func() { suite.tearDown(t) }) - registers the teardown.
  2. suite.setUp(t) - seeds the table.

The order of these two lines matters. If setUp() inserts one row and then fails, the teardown is already registered and still empties the table. The next subtest starts clean either way.

Both functions take the subtest’s t as a parameter instead of capturing the parent’s t. The reason is a rule of the testing package: t.Fatalf() must be called from the goroutine that runs the test. A subtest runs in its own goroutine, so a setUp() that calls the parent’s t.Fatalf() breaks that rule. The subtest’s t also makes the failure show up under the subtest’s name in the output. t.Helper() in setUp() makes the failure point at the subtest’s line, not at the line inside the closure.

The one difference from PHPUnit is that nothing invokes these functions for you. You have to manually write that 2 lines for each subtest. One advantage of this is its explicitness: anyone who reads a subtest sees exactly what state it starts from.

Use t.Cleanup instead of defer

t.Cleanup() registers a function that runs when the test and all its subtests complete. Functions registered on the same test run in reverse order of registration, like defer. They also run when the test stops early with t.Fatal().

In the example the subtest’s teardown runs first, when the subtest ends. The parent’s db.Close() runs last, after every subtest has finished. The connection is still open when each teardown needs it.

A defer in a subtest would work here too. The difference shows up with parallel subtests. Brandur Leach explains it in his “Prefer t.Cleanup with parallel subtests” article. When a subtest calls t.Parallel(), the test framework pauses it and lets the parent function return. A defer in the parent then runs at that return, before the paused subtests have run at all. If that defer closes the database, every parallel subtest gets a closed connection. t.Cleanup() is part of the testing framework, so the framework waits for the subtests before it calls the cleanup.

Use t.Cleanup() for anything a test sets up, then you never have to think about whether the test runs in parallel.

Combine the suite with a table

The test suite struct and a table can work together. Each case calls the same 2 lines before its own logic:

 1// This is a slice, the order fixed.
 2tests := []struct {
 3	name     string
 4	sku      string
 5	quantity int
 6	expected error
 7}{
 8	{name: "reserves available items", sku: "BOOK-1", quantity: 2},
 9	{name: "rejects an out-of-stock item", sku: "PEN-1", quantity: 1, expected: ErrOutOfStock},
10	{name: "rejects more than in stock", sku: "BOOK-1", quantity: 4, expected: ErrOutOfStock},
11}
12
13for _, tc := range tests {
14	t.Run(tc.name, func(t *testing.T) {
15		t.Cleanup(func() { suite.tearDown(t) })
16		suite.setUp(t)
17
18		if err := repo.Reserve(t.Context(), tc.sku, tc.quantity); !errors.Is(err, tc.expected) {
19			t.Fatalf("Reserve(%q, %d) error = %v, expected %v", tc.sku, tc.quantity, err, tc.expected)
20		}
21	})
22}

Run these subtests in parallel?

All subtests in the example share one stock table, and each teardown truncates it. If two of them ran in parallel, one subtest’s TRUNCATE would delete the rows another subtest is still reading. Leave t.Parallel() out of subtests that share a fixture this way.

To run database tests in parallel, give each subtest its own state:

  • its own transaction that it rolls back,
  • or its own schema.

Brandur Leach describes both approaches thoroughly in “On t.Parallel”.

Other tools in the testing package

Additionally, the testing package includes several other tools worth mentioning, alongside the ones listed above:

  • t.Context() returns a context that the framework cancels just before the cleanup functions run. Don’t use it inside a cleanup function, because it is already canceled there.
  • t.Setenv() sets an environment variable and restores the old value through t.Cleanup(). Because it changes the whole process, it fails in a parallel test or under a parallel parent.
  • t.TempDir() returns a temporary directory that the framework removes when the test and its subtests complete.
  • t.ArtifactDir(), new in Go 1.26, returns a directory for test output files. With go test -artifacts, the files stay under the output directory. Without the flag, the framework deletes the directory after the test.
